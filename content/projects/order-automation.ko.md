## 16개 동시 요청으로 API 대기시간 줄이기

주문 상세 API는 주문번호 하나당 한 번 호출해야 합니다. 한 요청이 끝난 뒤 다음 요청을 보내는 순차 처리에서는 응답을 기다리는 시간이 주문 건수만큼 쌓입니다. 이를 개선하기 위해 **Python `ThreadPoolExecutor` 기반 멀티스레드 방식으로 최대 16개의 상세 API 요청을 동시에 처리**했습니다.

한 스레드가 응답을 기다리는 동안 다른 스레드도 요청을 진행하므로, 여러 요청의 네트워크 대기시간이 겹칩니다. 실제 작업자 수는 `min(조회 대상 주문 수, 16)`이며, 응답 완료 순서가 달라도 결과는 입력 주문 순서에 맞춰 결합합니다. 개별 요청의 실패도 다른 요청을 중단시키지 않습니다.

**최초 대량 조회와 변경 주문 갱신에서 여러 요청의 대기시간을 겹쳐 처리**합니다. 작업자 수를 제한해 요청이 한꺼번에 무제한으로 증가하지 않도록 했으며, 작업이 끝난 건수로 진행률을 갱신합니다.

## 조회용 캐시 테이블로 반복 API 호출 줄이기

속도 최적화에서 크게 기여한 또 다른 부분은 **API로 한 번 받은 데이터를 저장하고 다시 사용하는 구조**입니다. ERP에서 가져온 주문 헤더·상세를 결합해 조회용 데이터마트처럼 활용하는 **CSV 캐시 테이블**을 두었습니다.

`pending_order_details.csv`에는 주문번호·순번, 품번·품명, 주문일·납기일, 수량과 수정일 등 조회에 필요한 필드를 저장합니다. 별도의 `sync_state.csv`에는 마지막 동기화 날짜와 캐시 검증 정보를 보관합니다. 화면 필터, 납기주별 집계와 엑셀 출력은 이 저장 데이터를 기준으로 처리합니다.

**ERP 수집 → 조회용 캐시 테이블 저장 → 화면 조회·주별 집계·엑셀 출력**으로 데이터 흐름을 구성해, 조건을 바꿔 다시 확인할 때도 전체 상세 API를 반복 호출하지 않도록 했습니다.

| 조회 시점 | 처리 방식 |
| --- | --- |
| 최초 조회·캐시 재구축 | 기준 기간의 주문 헤더와 상세를 받아 CSV 캐시 구성 |
| 날짜가 바뀐 첫 조회 | 전체 헤더에서 신규·수정·취소·삭제 상태를 대조하고 필요한 상세만 갱신 |
| 같은 날짜 재조회 | 유효한 저장 CSV에서 조건에 맞는 행을 읽어 표시 |

날짜가 바뀌면 헤더의 신규·수정 상태를 저장된 정보와 비교해 **갱신이 필요한 주문번호만 상세 API로 요청**합니다. 취소·삭제 주문과 납기가 지난 행도 정리해 캐시를 유지합니다. 예를 들어 기존 주문이 9,000건이고 신규·수정으로 선정된 주문이 3건인 경우, 상세 요청은 9,000회가 아닌 **3회**로 줄어듭니다. 이는 명세에 정의된 동작 예시입니다.

동시 처리가 한 번의 조회에서 대기시간을 줄인다면, 캐시는 반복 조회의 작업량을 줄입니다. **같은 날짜에 유효한 캐시를 다시 조회할 때는 헤더·상세 API 호출이 모두 0회**입니다. 백그라운드 작업의 단계와 완료 건수를 브라우저가 읽어 진행률을 표시하고, 사용자가 중지하면 새 상세 요청을 시작하지 않도록 했습니다.

캐시는 회사코드·스키마·조회일과 SHA-256으로 유효성을 확인합니다. 동시 갱신에는 잠금을 사용하고, 파일은 임시 파일 작성 후 교체합니다. 일부 조회가 실패하거나 이전 캐시로 결과를 보여줄 때는 불완전·최신성 상태를 전달하고 엑셀 다운로드를 제한해, 결과의 신뢰 범위를 화면에 드러냅니다.

## 출고장 엑셀을 생산 입력으로

현장의 기존 `.xls` 파일을 그대로 입력받도록 만들었습니다. 첫 번째 시트가 `일일출고장`인지 확인하고, **이월 → 입고 → 출고 → 재고**가 이어지는 표 블록에서 `자소` 품목을 찾습니다.

단순히 모든 셀에서 품목명을 검색하지 않고 표의 구조를 함께 확인합니다. 같은 품목명이 여러 열에 있어도 원본 셀 위치를 보존하고, 수식은 엑셀에 저장된 계산 결과를 읽습니다. 수식 결과가 없거나 오류이면 부분 결과를 성공으로 표시하지 않습니다.

![실제 XLS 파서로 읽은 예시 품목 6개. 현재 재고를 확인하면서 최소재고수량을 입력하며, 오른쪽 버튼으로 100단위 조절이 가능합니다.](../../../media/orders/inventory-input.jpg)

최소재고수량은 0 이상의 정수로 검증합니다. 날짜나 파일을 바꾸면 이전 입력 결과를 무효화하고 다시 확인하도록 했습니다. 완료된 입력은 날짜 조건·원본 품목·재고·최소재고를 묶은 `ProductionPlanInputSnapshot`으로 후속 계산에 전달합니다.

현재 화면의 **생성** 버튼은 계산 계층에 넘길 입력을 준비하는 단계입니다. 최종 생산계획표나 제조지시는 아직 생성하지 않습니다.

## 기능을 분리하고 실행 환경까지 연결

기능별 명세와 구현 모듈을 대응시키고, 실행 순서는 조립 계층에서 연결했습니다. 기능 모듈끼리 직접 의존하지 않게 해 날짜 검증·집계·엑셀 출력 등 각 규칙을 독립적으로 확인할 수 있습니다.

| 계층 | 책임과 설계 선택 |
| --- | --- |
| 웹 UI | HTML·CSS·JavaScript로 조회, 진행률, 검색·정렬과 재고 입력 구성 |
| Python 서버·조립 계층 | 요청 검증, 백그라운드 작업, 캐시 동기화와 기능 실행 순서 관리 |
| 기능별 모듈 | 날짜 조건, 헤더·상세 처리, Decimal 집계, XLS 해석, XLSX 생성 |
| ERP 공통 계층 | API별 요청 계약 분리, HMAC-SHA256 서명, 인증·오류 메시지 마스킹 |
| Windows 배포 구성 | PyInstaller·Inno Setup, 로컬 서버 런처, 순수 Python XLSX 어댑터 |

ERP 인증정보는 서버에서 처리하고 브라우저로 전달하지 않습니다. Windows 배포 구성은 런타임을 동봉하고 `127.0.0.1`에서 서버를 실행하는 방식으로, 사용자가 별도 개발 환경 없이 브라우저 UI를 여는 흐름을 준비했습니다. 설치기와 런처 코드는 구현되어 있으며 이번 포트폴리오 작업에서 설치 패키지의 고객 PC 운영까지 검증한 것은 아닙니다.

## 다음 단계: 생산 횟수와 보관재고의 균형

같은 품목의 여러 주 수요를 한 번에 생산하면 생산 횟수는 줄지만 보관재고가 늘어납니다. 다음 목표는 주문·현재고·최소재고와 생산능력 제약을 함께 사용해 **어느 주에 어떤 품목을 몇 개 생산할지** 결정하는 것입니다.

설계 문서에서는 납기 준수, 생산 횟수, 보관재고의 관계를 검토했습니다. 최신 제안은 17주 계획과 주별 품목 수·생산능력·최소 생산량 제약을 다루지만, 이전 문서와 다른 계획 기간 및 생산능력 해석은 최종 명세에서 확정해야 합니다. 최적화 모델 구현, 생산계획 엑셀과 공장 반영은 이후 단계입니다.

현재 성과는 **ERP 주문 → 조회용 캐시 → 확인 가능한 집계·엑셀 → 재고 기반 생산 입력**을 연결하고, 사용자 경험 기준 약 하루의 업무를 3분 이내로 줄인 것입니다. 재고 감소 효과는 후속 생산 최적화 단계에서 확인할 예정입니다.
